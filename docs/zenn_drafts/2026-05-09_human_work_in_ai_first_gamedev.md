> 本記事は個人開発中の HD-2D 探索アクションアドベンチャー **Anemora** の制作記録から、**「AI に渡した仕事 / 渡さなかった仕事」** の境界を振り返ったものです。プロジェクト概要は先行記事 ([Anemora 紹介記事](https://zenn.dev/marvelousu/articles/anemora-hd2d-time-frame)) を参照してください。

## 1. きっかけ — 「自分が何をしたのか」が分からなくなった

7 日間 AI エージェントを使って個人ゲーム開発の Vertical Slice を作っていたら、**自分が何の仕事をしたのか分からなくなる瞬間**がありました。

ピーク日 (2026-05-05) には Codex Pro が 1 日で 81 commit を push し、自動テスト 58 件が緑になり、Windows ビルドが成功し、orchestrator (当時は Claude) が「Stage 3 完成」と判定する。表面上、私の手はキーボード上であまり動いていない。

しかしビルドを起動すると、**画面には箱が 2 つ浮いているだけ**でした。音もなく、グラフィックもなく、操作も効かない。AI が出した「完成」と、私が起動して目にした「完成していない」の落差が大きすぎて、ここからすべての orchestration を一度書き直すことになりました。

落ち着いてから、過去 7 日間の記録を全部読み直して、**「自分本人が主語の moment」だけを抽出する**作業をしました。Anemora プロジェクトでは、各 task の制作日誌として `docs/devlog/YYYY-MM-DD_<topic>.md` を残し、セッションを跨ぐ context 引き継ぎは `~/notes/_handover/anemora-<topic>-YYYY-MM-DD.md` という形式で形式化しています。これらと、コミット履歴、postmortem、設定変更を合わせて読み直したわけです。

結果、私本人が主語の moment は 61 件出てきました。内訳はこうです。

| カテゴリ | 件数 | 比率 |
|---|---|---|
| 判断 (規模 / ジャンル / ネーミング / エンディング / QA sign-off) | 22 | 36% |
| 対話による創出 (メカ / 世界観 / 物語アーク を言語化) | 17 | 28% |
| 品質判定 (Scene 細部 / character asset / UI/UX) | 8 | 13% |
| 介入 (軌道修正 / 工数指摘) | 5 | 8% |
| 発見 (playable failure 等) | 5 | 8% |
| ルール化 (feedback memory 化) | 4 | 7% |
| キャパシティ運用 | 2 | 3% |
| 境界設計 (自律作業ガイドライン起草) | 2 | 3% |

「AI に任せて自分は何もしていない」という体感とは裏腹に、**判断と創出だけで全 moment の 64%** を握っていた。手を動かしている感覚が薄れていただけで、仕事は人間側に集中していました。

この記事では、この 61 moment を **「渡せた仕事 / 渡せなかった仕事」の 2 列**で整理し、渡せなかった側に共通する **3 つの本質的な仕事** を言語化していきます。

## 2. プロジェクトと体制の概観

7 日間で起きたことを少しだけ俯瞰します。

| 日付 | commit 数 | 主な動き |
|---|---|---|
| 5/4 | 26 | Stage 1 (コンセプト) + Stage 2 (PITCH / SPEC) の対話、プロジェクト名「Anemora」確定 |
| 5/5 | 81 | Stage 3 Vertical Slice 実装ピーク、5 セッション並列で URP / 実装 / アセット / 音 / 公開向け doc 同時進行 |
| 5/6 | 28 | Stage 3 closeout + Stage 4 entry、VS playable failure 修復 |
| 5/7 | 4 | Stage 4 — character review、自律作業ガイドラインの起草 |
| 5/8 | 3 | Chapter 1 設計 corpus + 本記事 draft |
| 5/9 | 9 | Chapter 1 Scene 1-5 design (詳細詰め) |
| 5/10 | 1 | Chapter 1 dialogue cross-scene pin (現在進行中) |

**累計 152 commit / 228 件以上の handover** が 7 日間で動いています。

注目したいのは、**日ごとに「並列の張り方」がガラッと変わっている**ことです。5/5 のピーク日は 5 セッションで実装を並列に走らせる形でしたが、5/6 以降の Stage 4 では同じ並列構造ではなく、テーマ単位 (chapter1 設計 / character 反復生成 / map 生成 / graphics integration) のセッションを必要に応じて立てる形に切り替えました。Windows 側の Unity worktree も 7 日間で 25 個以上が作られています。

つまり「AI を並列で何セッション動かすか」は **固定値ではなく、その日に何をやりたいかで毎日違う形を取っている**。その上で、私が 7 日間ずっと握り続けた仕事を抜き出していきます。

## 3. 渡せた仕事 / 渡せなかった仕事

7 日間で起きたことを 2 列に分けると、こうなります。

| 渡せた仕事 (= AI が自律で進められた) | 渡せなかった仕事 (= 私が握り続けた) |
|---|---|
| sprite / 3D / BGM / SFX / フォント atlas の **生成** | 何を作るかの **創出** (メカ・世界観・物語アーク) |
| C# 実装 / asmdef 分割 / ScriptableObject 設計 | 「これは違う」「もっとシンプルに」の **方向修正** |
| EditMode / PlayMode テストの起草 | 「テストが通った = 完成」ではないことの **判定** |
| Windows Standalone build / asset bundle 生成 | 起動して画 / 音 / 操作を確かめる **playable verification** |
| 並列セッションへの task dispatch / 進捗集約 | 並列幅・session 形態の **キャパシティ運用** |
| ADR 起草 / CHANGELOG / 公開向け doc | キャラ / Scene / dialogue の **subjective review** |
| 計画書 v1 → v2 改善 (cross-model review) | 「ここから先は私が判断する」の **境界線設計** |
| commit / push / PR 起票 | feedback の **ルール化** (memory への永続化) |

左列は数で言えば莫大です。152 commit / 228 件以上の handover / 自動テスト 58 件 pass / アセット生成数十点を 7 日で。右列は数で言えば 61 件、しかし **どれ一つ抜けてもプロジェクトが壊れる** 種類の仕事でした。

右列をさらに俯瞰すると、**3 つの本質的な仕事** に集約されます。

1. **創出** — まだ存在しないものを言葉にする (28%)
2. **判定** — 自動化が「OK」と言った後で「本当にそうか」を確かめる (49%、判断 + 品質判定 + 発見の合算)
3. **境界** — AI が自律で動く範囲と、人間判断に escalation する範囲を線引きする (10%、ルール化 + 境界設計)

以下、それぞれ具体 moment を挙げていきます。

## 4. 渡せなかった仕事 1 — 創出

### 4.1 「文明 → 廃墟 → 文明 のループに違和感がある」

Stage 1 のコンセプト対話 (`CONCEPT.md` を作っていた段階) で、それまで議論していた世界観の骨組みに対して、私が一言「文明 → 廃墟 → 文明のループは無理やり感がある」と指摘しました。これがきっかけで、世界の時間構造そのものが書き直しになり、結果として **物語アークと核メカニクスを一気通貫で説明できる構造** に再構成されました。

このときの Claude の動きは、**壁打ち相手 + 構造化担当**としては優秀でした。私が断片的に出した違和感を構造化された候補に変換し、複数案を並列に並べ、整合性をチェックしてくれた。ただし **「違和感を言葉にする」「これは違う」と感じる**ことそのものは、AI 側からは出てこない仕事でした。

### 4.2 「2D 的表現でいきたい」

同じ Stage 1 で、当初の議論では 3D 視点も選択肢に入っていました。私は TPS / FPS というジャンル自体は好きで個人的には数万時間は遊んでいるのですが、**今回作りたいゲームの方向性とは違う**と感じていました。「2D 的表現でいきたい、TPS / FPS の文法とは別の経路で行きたい」と伝えたところ、視点 / カメラ / アート方針が **完全固定アイソメ** に確定し、以降の技術選定 (Unity URP、HD-2D、PixelLab + Aseprite パイプライン) はすべてこの 1 行から逆算されました。

「自分の好み」と「今作りたいもの」を切り分けて方向を伝えるのは、案外 AI からは引き出せない種類の判断だと感じました。

### 4.3 ネーミング — 2 ラウンドのブレスト

プロジェクト正式名「Anemora」(Anemoia 短縮派生 + Memoria) は、日本語 18 候補 → 英数 18 候補 → 最終 2 案比較、というブレスト工程で確定しました。Claude は候補生成と意味検証 (語源 / 既存タイトル被り / 商標) を担当、私は **「読んだとき / 口に出したときの感覚」**で振り落としていきました。

このパターンが何度も出てきます。**創出フェーズで AI は候補生成と整合性チェックに有効、ただし「これにしよう」「これは違う」の最終判断は人間側に残る**。

## 5. 渡せなかった仕事 2 — 判定

### 5.1 きっかけ: 「箱が 2 つ浮いているだけだった」

§1 で書いた事件を、ここで詳しく扱います。Stage 3 期間中は他にも大小の課題が出ていましたが (URP の警告、TMP atlas の missing chars、audio loudness ばらつき等)、orchestration の前提を一番ぐらつかせたのが **VS (Vertical Slice) の起動失敗** でした。

orchestrator (当時 Claude) が「Stage 3 完成」と判定した根拠は次のものでした。

- PlayMode テスト 27/27 / EditMode テスト 31/31 が緑
- Windows Standalone ビルドが成功 (compile + asset bundle 生成 OK)
- 自動 G5 checklist の "Go" 判定
- 起動時間 7.934 秒 / GPU peak 78.4 MiB の数値計測 OK

しかし、これらすべて **「Editor 側で計測されたもの」** か **「自動計測スクリプトの出力」** で、**実際に exe を起動して画 / 音 / 操作を確かめた人** は誰もいませんでした。

実際の bug は素朴で、ビルド設定の scene index 0 が `Sandbox_E1_Stencil` のまま (本来は `Anemora_Main` になっているべき) でした。Editor 上で `Anemora_Main` を直接 Play すると正常動作するため、**PlayMode テストでは検出できない**。AI が見ていた緑のテストはすべて Editor 経由で、Standalone ビルドの起動経路は誰もテストしていなかったわけです。

これを発見できるのは「ビルドを起動して画面を見る人」だけです。**AI が verify できる領域と、人間しか verify できない領域** の境界を、事前に明文化していなかった構造的問題でした。事後にこの境界を 2 列に分けて記録しています。

| AI が verify 可能 | 人間しか verify できない |
|---|---|
| 入力 → state 変化の観察 | audio の体験的心地よさ |
| Player position / dialogue UI 表示 | visual の美意識 |
| portal trigger / audio source play state | 5〜8 分の通し体験の engagement |
| screenshot / Player.log 解析 | dialogue の文脈・余韻 |
| Input wiring の存在確認 | gameplay の "playable" 判定 |

### 5.2 character / Scene のミクロ判定

判定はマクロな完成判定だけでなく、ミクロにも残ります。Stage 4 では sprite 生成パイプライン (PixelLab → Aseprite → Unity import) を回しているのですが、character の **proportion lock 候補を v6 → v10 まで反復**させたのち、最終的に「これでいく」と決めるのは私の仕事でした。

第 1 章 Scene 1 の最終調整では、AI が出した dialogue 案に対して、私が「この章の前半は観察のみで因果を発生させない設計ルール」と照合し、**ある演出 (本が出現するギミック) を削除**しました。AI は dialogue としては自然な案を出していますが、章のメカニクス・ルールとの整合性は私が握っているので、見つけられるのは私だけでした。

数で言えば、こうした品質判定の moment は 61 件中 8 件 (13%)。ただし「ここで削除しなければ、その演出は完成版にも残ってしまう」という不可逆な決定なので、件数の重みは数より重く感じます。

## 6. 渡せなかった仕事 3 — 境界

### 6.1 自律作業ガイドラインの起草

VS failure の事件以降、AI が **どこまで自律で進めてよく、どこから人間に escalation すべきか** を明文化する必要を感じて、`docs/AUTONOMOUS_WORK_GUIDELINE.md` を 1 本起草しました。骨子はこうです。

```
## 進められる作業 (干渉不要、独自判断 OK)
- グラフィック polish (既存 Tier 範囲内)
- パフォーマンス改善 (Profile 確認、ボトルネック解消)
- バグ修正 / テスト追加
- ドキュメント整備
- 既存仕様の整合性検証 (レポートのみ、判断変更しない)

## 進められない作業 (要ユーザー判断、独自進行禁止)
- 物語 / 世界観の核心判断
- 新規メカ / 美術スタイルの大幅変更
- 公開 / リリース判断
- ストーリー doc の編集を含む commit
```

AI が自律で動ける範囲を広げたいが、広げるほど **誤った "完成" 判定や "確定" 判定が混入するリスクが上がる**。ここの線引きは、プロジェクトを進めるうちに自分の判断軸として育っていくものでした。

### 6.2 feedback の永続化

境界線は document だけでなく、**個別の挙動制御ルール** としても残します。VS failure 後、私が永続化した feedback は以下です。

- `feedback_anemora_no_premature_lockin` — 「複数案を維持し、ユーザーが『決めた』と明示するまで lock しない」
- `feedback_anemora_user_review_required` — 「ユーザー体験確認なしで Stage 完成宣言しない」
- `feedback_anemora_test_pass_vs_playable` — 「test pass / build success ≠ playable」
- `feedback_anemora_no_recommend_pushing` — 「『(推奨)』表記を多用しない」(意思決定圧力の制御)
- `feedback_anemora_no_spoiler_in_metadata` — 「ネタバレ語彙を外部見える場所に書かない」

これらはセッションを跨いで持ち越す **永続的なルール** で、毎回の会話の冒頭で AI に再ロードされます。一度書けば二度と同じ過ちを言わせない、という形で AI の挙動制御に効きます。

## 7. キャパシティ運用 — 番外編

ここまでの 3 つに加えて、頻度は少ないが本質的に重要な仕事として、**並列幅とセッション形態の運用** がありました。Codex Pro の週間制限が接近したタイミングで `graphics-foundation` セッションを Codex から Claude に handoff したり、Stage 3 期は windows worker 並列だった構造を Stage 4 では theme-based session (chapter1 / character / map / graphics) に組み直したり。

「いつ・どの形のセッションを立てるか」の判断は、自動化しようと思えばできなくはないのですが、**プロジェクトの今のフェーズと、自分が今何を一番進めたいか**を照合しながら決めていくので、結局私の手元に残っていました。

## 8. まとめ

7 日間で起きたことを振り返ると、**「AI に任せたら自分は何もしなくなる」**という直感は半分外れていました。手を動かす量は確かに減るが、仕事の質は **「実装」から「創出 × 判定 × 境界」に集中** する。

| 仕事 | フェーズ別の濃度 |
|---|---|
| 創出 | Stage 1-2 (コンセプト対話) で集中、Stage 3 以降は少 |
| 判定 | 全フェーズで継続、特に Stage 3-4 で増加 |
| 境界 | failure 事件後に集中起草 (gateway moment) |

AI が手を動かす個人開発で「人間がやること」は **減らないし、軽くもならない**。むしろ自動化されない領域に **集中する** ので、密度が上がります。同じ 7 日でも、創出と判定と境界線設計に費やしたエネルギーの量は、自分で実装していた頃と変わらないか、もしかすると増えています。

Anemora 本体の制作は今 Stage 4 の中盤で、Chapter 1 の Scene 設計と graphics integration が並走中です。次の節目で、また「自分が何をやって、何を AI に渡したか」を整理し直してみる予定です。
