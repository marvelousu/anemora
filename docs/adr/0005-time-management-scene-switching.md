# ADR-0005: 時間管理 / シーン切替の実装方針

## Status

Accepted (実装は Stage 3 E トラックで検証 → 必要なら改訂)

## Date

2026-05-04 (Stage 3 Day 0)

## Context

Anemora の中核機構「時の窓 (Time Frame)」のレンダリング方針は ADR-0002 で確定したが、実際にプレイヤーが踏込み・帰還・能動行動・痕跡可視化を体験するための **状態管理 / シーン切替 / 時間制御** の詳細は別 ADR で定義する必要がある。

### ADR-0002 から繰延された項目 (本 ADR で確定)

1. **踏込み時のシーン主従反転** — プレイヤーがポータル平面を越えたフレームで、メインシーンとポータル内シーンの主従が反転する詳細メカニクス
2. **ポータル用シーンのライフサイクル** — 常駐ヒエラルキー or Additive ロード のどちらか (ADR-0002 でこの選択を本 ADR に投げた)
3. **時間侵食状態の状態遷移定義** — ADR-0002 で「描画機構の制約」と「ゲーム状態遷移」を分離、本 ADR が後者を定義

### 機能要件 (SPEC.md / VS_SCOPE.md より)

| 要件 | 出典 |
|---|---|
| 枠生成中は時間がスローモーション or 停止 (TBD) | SPEC §5.1.1 |
| 踏込み中も現在世界の時間は止まっている (TBD) | SPEC §5.1.1 |
| 過去で能動行動 → 現在に痕跡反映 | SPEC §5.2 / VS_SCOPE §3.1 |
| 時間侵食状態時のみ描画不可 (VS では発動させない) | SPEC §2.5 / VS_SCOPE §3.1 |
| 詰み防止: 何度でも再描画可能、時間侵食はリトライで解除 | VS_SCOPE §3.1 |
| オートセーブ: ゾーン入場 / 時の窓使用後 / 重要会話後 | SPEC §5.4 / VS_SCOPE §6 |
| 層遷移時にルールが書き換わる (VS は層 1 + 層 2 片鱗) | SPEC §3.3 / VS_SCOPE §2 |

### 制約

- Unity 6.3 LTS + URP (ADR-0001)
- ADR-0002 (Time Frame ポータル) と整合
- ADR-0007 (UI フレームワーク) のシンボル選択 UI / 対話 UI と連携
- ADR-0006 (セーブシステム、未起草) と境界を定義
- VS では赤シンボル (過去) + 持ち帰る 1 種のみ実装、未来側は演出のみ
- VS では時間侵食状態を発動させない (機構は定義するが、トリガー条件を満たさない)

## Decision

### 1. 踏込み時のシーン主従反転

#### 反転トリガー条件

- プレイヤーの位置が **ポータル平面の法線方向に対してどちら側にいるか** で判定
- フレーム単位で監視 (Update / FixedUpdate)
- 越えた瞬間 (前フレームと今フレームで側が変わった) に **加えて、最小移動量を満たした場合のみ** 反転処理を発動
- 境界付近の往復ノイズを避けるため、**ヒステリシス帯** を持たせる (反転判定の閾値に余白)

#### 反転処理の詳細

| 対象 | 反転前 (現在側) | 反転後 (過去側) |
|---|---|---|
| **メインカメラ** | 現在シーン主、ポータル内が過去シーン | 過去シーン主、ポータル内が現在シーン |
| **Stencil テスト方向** | 現在=ステンシル外、過去=ステンシル内 | 過去=ステンシル外、現在=ステンシル内 |
| **プレイヤーの所属シーン** | 現在シーン | 過去シーン |
| **衝突判定 / 物理** | 現在シーンの Collider が有効 | 過去シーンの Collider が有効 |
| **NPC / オブジェクトの活性** | 現在シーンが活性、過去シーンは描画のみ | 過去シーンが活性、現在シーンは描画のみ |
| **UI** | 現在用 HUD / 対話 UI | 過去用 HUD (赤色調)、対話 UI は引き続き機能 |

#### 物理レイヤー切替

- 現在側 / 過去側の Collider は **レイヤー分離** する (例: `Layer_Current_Collider` / `Layer_Past_Collider`)
- 反転時はプレイヤーの衝突レイヤーを切替える
- **境界上では両側の Collider を同時有効化しない** (擦り抜け / 詰まりの防止)
- 反転完了後に **不要側の衝突レイヤーを無効化** する

#### フレーム遷移演出

- 反転フレームに **微細な視覚遷移** (一瞬の白フェード / 色シフト等) を入れる (Stage 3 で具体化)
- 急峻な切替で違和感を出さない、しかし長すぎる演出は VS の体験を損なう (1 秒以内目安)

### 2. ポータル用シーンのライフサイクル

**Decision: 1 シーン + 常駐ヒエラルキー方式を採用 (Additive ロードは VS では不採用)**

#### 採用理由

- VS は **第 1 ゾーン (現在) + その過去 1 つ** のみのスコープ (VS_SCOPE.md §3.2)
- **Unity Scene は 1 つを基底** とし、その内部に `Root_Current` / `Root_Past` を **常駐 GameObject 群** として保持
- レイヤー分離で別カメラに描画 (ADR-0002 採用方針)
- メモリオーバーヘッドが小さい (低ポリ 3D + 軽量ドット絵スプライト前提)
- シーン切替遅延がない (Additive ロード待ちが不要)
- 状態同期が単純 (ロード/アンロードによる初期化漏れを回避)

#### 構造

```
Unity Scene (1 つ、基底):
├── Root_Current (現在世界、常駐 GameObject 群)
│   ├── Buildings_Current
│   ├── NPCs_Current
│   ├── Player_Position_Current (プレイヤー位置参照)
│   └── Layer: "Current"
└── Root_Past (過去世界、常駐 GameObject 群)
    ├── Buildings_Past
    ├── NPCs_Past
    ├── (能動行動の対象オブジェクト)
    └── Layer: "Past"
```

カメラ:
- メインカメラ: culling mask = Current レイヤー
- ポータル内側用カメラ: culling mask = Past レイヤー
- 反転後はカメラの culling mask を切替 (or カメラ自体を交換)

#### Stage 4-5 での再評価

- ゾーン数が増える / 時代数が増える場合 (白=現在 / 青=未来 が追加される Stage 4 以降) は **ゾーン単位で Additive ロード方式に切替** を検討
- 切替判断は ADR-0005 の改訂 or 別 ADR (Superseded) で記録

### 3. 時間スローモーション / 停止 (枠生成中)

**Decision: 枠生成中は Time.timeScale = 0 (完全停止) を採用する。踏込み中は別方針とし、Stage 3 で具体化する。**

#### 詳細

| 状態 | 現在シーンの時間 | 過去シーンの時間 |
|---|---|---|
| 通常プレイ | 通常進行 | 停止 (描画のみ) |
| 枠生成中 (シンボル選択 UI 表示中) | **完全停止** (Time.timeScale = 0) | 停止 |
| 踏込み中 (過去シーン主) | 停止 (描画のみ、現在は静止) | **Stage 3 で別方針を確定** |
| 帰還後 (現在シーン主に戻る) | 通常進行 | 停止 |

#### 踏込み中の時間制御方針 (Stage 3 で確定)

`Time.timeScale = 0` は踏込み中には維持しない (Unity の全体 timeScale と「片側だけ進む」は両立しないため)。Stage 3 E トラックで以下のいずれかを実機検証して確定:

- **A. 全体 `timeScale` を通常に戻し、過去側オブジェクトのみ個別停止する**
  - 現在側のすべてのオブジェクト (Animator / Rigidbody / NPC スクリプト) を個別に停止
  - 過去側はそのまま進行
- **B. 独自のシーン内時間系を持ち、過去側のみ進行させる**
  - `Time.timeScale = 0` を維持し、過去側オブジェクトを `unscaledDeltaTime` ベースで動かす
  - 実装複雑度高、Stage 3 で見積もり

本 ADR では「枠生成中のみ完全停止」とし、踏込み中の実装詳細は Stage 3 で確定する。

#### 理由

- 完全停止のほうが UI 操作 (シンボル選択ホイール) が安定
- スローモーションは「中途半端」で違和感が出やすい
- 踏込み中に現在の時間が止まることで、過去/未来の体験を「外側から覗く」感覚を強化

#### 実装 (枠生成中)

- `Time.timeScale = 0` で完全停止
- UI / シンボル選択ホイールは **`Time.unscaledDeltaTime`** を使う
- BGM 等の Audio は `AudioSource.ignoreListenerPause = true` 等で停止しない設定

#### 補足 (timeScale = 0 時の挙動と副作用)

- UI は `unscaledDeltaTime` で更新する
- `Animator` は **UI 用とワールド用で更新モード (`UpdateMode`) を分ける** (UI Animator は `UnscaledTime`、ワールド Animator は `Normal`)
- `Rigidbody` / `FixedUpdate` に依存する挙動は枠生成中に進行しない前提とする
- `Timeline` / `NavMeshAgent` も停止する (副作用として認識、Stage 3 で個別対応)
- 物理が必要な演出は `unscaledDeltaTime` ベースの個別更新か、アニメーション駆動に寄せる
- プレイヤー移動、NPC 移動、衝突解決のうち **枠生成中に止める対象を Stage 3 で確定** する

### 4. 時間侵食状態の状態遷移定義

**Decision: 時間侵食状態を機構として定義する。VS では発動条件を満たさない (詰み防止)。**

#### 状態遷移

```
通常状態 ──[発動条件]──▶ 時間侵食状態 ──[解除条件]──▶ 通常状態
```

- **発動条件**: VS では設定しない。Stage 4 で具体化 (例: 同一物体を 3 回連続持ち帰る、過去への過剰干渉など)
- **解除条件**: 時の窓を再描画 → 自動解除 (詰み防止のため、複雑な解除条件は設けない)
- **状態の効果**: 一時的に枠生成不可 + 視覚的なフィードバック (画面の歪み等)

#### VS での扱い

- 機構は実装するが、発動トリガーを与えない (VS_SCOPE.md §3.1 詰み防止)
- 状態遷移のテストは Stage 4 で行う (VS では「通常状態固定」で運用)

### 5. 痕跡可視化 (現在反映) のトリガーとデータフロー

#### データフロー

```
[過去で能動行動]
    │
    ▼
[ActionRecordEntry を生成] (永続化対象のプレイ履歴 DTO)
    │
    ▼
[ActionRecordStore に追加]
    │
    ▼
[帰還トリガー: プレイヤーが現在側に踏み戻った瞬間]
    │
    ▼
[ActionRecordStore をスキャン]
    │
    ├──▶ 該当する現在シーンのオブジェクトに「痕跡」を付与
    │       - 失われたオブジェクト (本 / 樹) を非表示化
    │       - 新しい NPC セリフを有効化 (生存・移住・会話変化)
    │       - 光の粒 / 色の変化 / 環境音の変化
    │
    └──▶ UI: 進行ログに記録 (ADR-0007 §進行ログ で扱い)
```

#### データ構造 (3 層分離、Stage 3 で実装詳細確定)

ScriptableObject 誤用を避けるため、永続化対象と静的定義を **明確に分離**:

| 層 | 役割 | 実装形式 | 永続化 |
|---|---|---|---|
| **ActionRecordEntry** | プレイ履歴の DTO | C# クラス (Plain Old Object) | セーブデータ内に保存 |
| **ActionRecordStore** | ランタイム履歴の保持領域 | C# クラス (List<ActionRecordEntry>) | セーブ / ロード対象 |
| **ActionRecordCatalog** | 静的定義カタログ (対象オブジェクト ID / 行動種別 / 痕跡種別の対応表) | **ScriptableObject (アセット資産)** | 永続化しない (アセットとして読込のみ) |

```csharp
// プレイ履歴の DTO (永続化対象、セーブデータに含まれる)
public class ActionRecordEntry {
    public string actionId;        // "carry_book_from_past"
    public string targetObjectId;  // "book_a_in_main_house"
    public ActionType type;        // 持ち帰る / 告げる / 押す
    public long gameTimeTicks;     // ゲーム内時刻 (DateTime ではなく long で安定化)
    public bool reflected;         // 現在に反映済か
}

// ランタイム履歴の保持 (セーブ / ロード対象)
public class ActionRecordStore {
    public List<ActionRecordEntry> entries;
}

// 静的定義カタログ (ScriptableObject アセット、永続化しない)
[CreateAssetMenu(menuName = "Anemora/ActionRecordCatalog")]
public class ActionRecordCatalog : ScriptableObject {
    public List<CatalogEntry> entries;
    // 各 actionId に対応する痕跡種別 / 対象オブジェクト ID 群を定義
}
```

> **重要**: `ScriptableObject` をランタイム履歴の保持に使わない。アセット資産とセーブデータの混線を避けるため、`ActionRecordEntry` / `ActionRecordStore` は通常クラス、`ActionRecordCatalog` のみ ScriptableObject。

#### Visual の責務分担

- **痕跡可視化のシェーダ / VFX** = ADR-0002 の Renderer Feature を流用
- **NPC セリフの分岐** = ADR-0007 (UI / 対話 UI) と連携、ActionRecord を参照して表示テキスト切替
- **環境音の変化** = ADR-0003 (アセットパイプライン) の SFX、ActionRecord トリガーで再生

### 6. セーブ / ロード時のシーン状態復元

**Decision: 本 ADR では「プレイ進行に意味がある状態」のみをセーブ対象として定義し、永続化方式は ADR-0006 で確定する。**

#### セーブ対象データ範囲 (本 ADR が定義)

| 範囲 | 内容 |
|---|---|
| プレイヤー状態 | 位置、向き、所属シーン (現在 / 過去) |
| ActionRecordStore | 全エントリ (痕跡反映の元データ、`ActionRecordEntry` の List) |
| 進行フラグ | 層進行 (1〜5 + 真層)、ゾーン解放、サイドクエスト |
| 時間管理状態 | 時の窓の状態 (生成中 / 踏込み中 / 通常) |
| アクセシビリティ設定 | UI 拡大率 / 字幕サイズ / コントラスト (ADR-0007 と連携) |

#### セーブ対象外 (一時状態、復帰時に再生成)

- 開いている対話 UI
- 進行ログの表示状態
- インベントリの開閉状態
- `Time.timeScale` (起動時に通常値で初期化)
- 一時的な演出フラグ (フェードイン / アウト等)

#### オートセーブのトリガー

- ゾーン入場時
- 時の窓使用後 (能動行動が完了して現在に戻った後)
- 重要会話後 (主要 NPC との対話完了時)
- ESC メニューを開いた時

#### ADR-0006 (セーブシステム、未起草) との責務分担

| 責務 | 担当 ADR |
|---|---|
| **セーブ対象データの意味と範囲** | 本 ADR (0005) |
| **ファイル形式** (JSON / Binary 等) | ADR-0006 |
| **保存先** (PersistentDataPath / Steam Cloud) | ADR-0006 |
| **スロット管理** (1-3 スロット、メタデータ) | ADR-0006 |
| **ロード順序** (どの順でデシリアライズ・適用するか) | ADR-0006 |
| **暗号化 / 圧縮** の要否 | ADR-0006 |

### 7. 層遷移演出との連携

VS では **層 1 + 層 2 への片鱗 1 カット** のみ実装する (VS_SCOPE.md §3.4)。**ルール本体の変更は Stage 4 で行う**。

- 層遷移の **トリガー** = 進行フラグの達成 (層進行フラグ、SPEC §5.3)

#### VS で実装する処理 (演出のみ)

- **片鱗演出** (VFX / BGM / 画面変化) — ADR-0002 Renderer Feature 流用、ADR-0003 BGM 切替
- **進行ログの演出上の更新** — SPEC §9 / ADR-0007 の対話 UI / 進行ログで反映

#### Stage 4 で実装する処理 (ルール本体)

- **ルール変更本体** (能動行動の効果が変わる、痕跡可視化のロジックが変わる)
- **層遷移後のシステム切替** (ActionRecordCatalog の差替、痕跡判定ロジックの分岐)
- **進行ログの実体的書換** (層 2 以降の世界観に応じた記録の意味変更)

## Consequences

### 利点

- **ADR-0002 と密結合する状態管理が一箇所に集約** — 後続実装で「どこで何を管理するか」が迷わない
- **常駐ヒエラルキー方式が VS スコープに最適** — メモリ・遅延・状態同期のシンプルさが両立
- **痕跡可視化のデータフローが明文化** — ActionRecord 中心の設計で、視覚 / NPC セリフ / UI の責務が分離
- **時間制御の方針 (完全停止) が決まる** — 枠生成中の UI 操作と踏込み中の時間流れが両立
- **時間侵食機構は定義するが VS では発動させない** — 詰み防止と将来拡張の両立
- **セーブ対象データ範囲が定義される** — ADR-0006 (セーブシステム) で永続化方式に集中できる

### 欠点 / 注意点

- **常駐ヒエラルキーは Stage 4-5 でゾーン / 時代が増えると見直し必要** — Additive ロードへの切替判断点を Stage 4 入口で再評価
- **シーン主従反転は実装の繊細さを要する** — フレーム単位の判定、衝突判定の有効/無効、Stencil 反転が同期する必要、Stage 3 E トラックで実機検証必須
- **完全停止 (Time.timeScale = 0) は Audio / UI に注意** — `unscaledDeltaTime` 使用、Audio は停止しない設定にする工夫
- **ActionRecord の永続化** — 大量のアクション記録が発生した場合のセーブデータサイズ膨張、Stage 4 以降で計測
- **層遷移時のルール変更ロジック** — 本 ADR では概念定義のみ、Stage 4 で具体実装 (VS では片鱗のみ)

### 後続への影響

- **ADR-0002 (Time Frame ポータル)** — 本 ADR が踏込み遷移詳細とライフサイクルを確定したため、ADR-0002 の「ADR-0005 で詳細化」記述が解決
- **ADR-0006 (セーブシステム、未起草)** — 本 ADR との責務分担を明文化:
  - **本 ADR (0005)**: セーブ対象データの意味と範囲
  - **ADR-0006**: ファイル形式 / 保存先 / スロット管理 / ロード順序 / 暗号化・圧縮の要否
- **ADR-0007 (UI フレームワーク)** — 進行ログの書換、対話 UI の状態切替、シンボル選択 UI の枠生成中操作で連携
- **VS_SCOPE.md §3.1 / §3.4** — 詰み防止 (時間侵食非発動) / 層 2 片鱗演出が本 ADR で具体化
- **SPEC.md §5 (Systems)** — 時の窓 / 能動行動 / 進行管理が本 ADR の状態遷移と整合

## Alternatives

### 候補 B: Additive ロード方式 (シーン動的ロード)

**実装:** ポータル生成時に過去シーンを Additive ロード、ポータル消去時にアンロード

**利点:**
- メモリ効率が良い (使う時だけロード)
- ゾーン / 時代が増えても拡張しやすい

**欠点:**
- ロード遅延 (枠生成時にラグ)、VS の Day 0-10 スコープでの実装難度が高い
- VS の規模 (1 ゾーン + 1 時代) では恩恵が小さい
- 状態同期が複雑 (ロード/アンロード時の初期化処理)

**判定:** **不採用 (VS で)、Stage 4-5 で再評価**。Anemora の VS スコープでは常駐ヒエラルキーが最適。

### 候補 C: 完全独立シーンファイル + Scene Manager 切替

**実装:** 現在 / 過去をそれぞれ別の `.unity` シーンファイルとして保持、SceneManager.LoadScene で切替

**利点:**
- 開発時のシーン編集が独立
- 大規模ゲームで一般的

**欠点:**
- ポータル内側に「別シーンを描画する」要件と相性が悪い (一度に 1 シーンしかアクティブにできない、Additive で複数アクティブにする必要)
- ステンシルポータル方式と組み合わせる場合、結局 Additive ロード相当になる

**判定:** **不採用**。Anemora のポータル方式と整合しない。

### 候補 D: 時間制御を スローモーション (Time.timeScale = 0.1)

**実装:** 枠生成中を完全停止ではなくスローモーション

**利点:**
- 「時を止めた」感ではなく「時を曲げた」感、Anemora の世界観に近い質感
- 時の窓ポータルの「立体ジオラマが立ち上がる」演出と整合

**欠点:**
- UI 操作 (シンボル選択) が時間と紐付くと操作感が悪い
- スローモーション中に現在世界が中途半端に動くと違和感

**判定:** **将来採用候補 (保留)**。VS では完全停止を試し、Stage 4 でユーザー体験次第で再評価。

### 候補 E: 痕跡可視化を即時反映ではなくフレーム遅延

**実装:** 過去で能動行動した瞬間に現在世界を即時更新 (ポータル越しに見える)

**利点:**
- プレイヤーが「行動 → 結果」を直接観察できる、フィードバックが強い

**欠点:**
- ポータル越しに同時表示すると Stencil 計算が複雑化、ADR-0002 の単純実装方針と矛盾
- 現在世界の状態管理が複雑 (リアルタイム同期)

**判定:** **不採用**。VS では帰還後の差分反映方式 (本 ADR §5) を採用。

## 検証ポイント (Stage 3 E トラックで実機確認)

### 機能動作

1. **シーン主従反転の正確性** — プレイヤーがポータル平面を越えた瞬間、衝突判定 / カメラ / Stencil 方向が同期して反転するか
2. **常駐ヒエラルキー方式のメモリオーバーヘッド** — VS スコープ (1 ゾーン + 1 過去) で許容範囲か、Stage 4 でゾーン増加時の見直し基準を計測
3. **完全停止時の UI 操作** — `Time.timeScale = 0` 中にシンボル選択ホイールが正常動作するか (`unscaledDeltaTime` 使用確認)
4. **Audio の停止しない設定** — 完全停止中に BGM / 環境音が停止しないか
5. **痕跡可視化のトリガー** — 帰還時に ActionRecord が正しくスキャンされ、該当オブジェクトに痕跡が付与されるか
6. **オートセーブの安定性** — 各トリガー時にセーブが正常完了するか、シーン状態の復元が完全か (ADR-0006 と連携検証)

### 体験

7. **踏込み遷移の自然さ** — フレーム遷移演出 (微細な視覚遷移) が違和感なくプレイヤーに受け入れられるか
8. **時間停止の体感** — 完全停止 vs スローモーションの体感差を VS 試作で評価、Stage 4 で再評価判断
9. **痕跡可視化の効き** — プレイヤーが「行動が世界を変えた」と感じられる演出強度 (光の粒 / 色変化 / NPC セリフ)

### エッジケース

10. **詰み防止の確認** — 時の窓再描画でいつでも状態解除できるか、時間侵食が VS 中に偶然発動しないか
11. **層遷移時の状態整合性** — VS の層 2 片鱗演出後に状態が正しく層 2 ルールへ移行するか (VS では「予兆 1 カット」のみだが、機構として整合確認)

検証で破綻が出たら本 ADR を改訂、または別 ADR (Superseded) で記録する。
